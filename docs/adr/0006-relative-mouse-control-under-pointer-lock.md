# Player control is relative mouse movement under Pointer Lock, not cursor-position following

The ship no longer eased-follows the cursor's absolute position. Instead the mouse acts as a **relative steering device**: each frame we accumulate raw `movementX/Y` deltas, normalize them into virtual space, and shove a free-floating target point by `delta · sensitivity`; the ship then eases toward that target with the existing exponential smoothing. The cursor's on-screen position is now irrelevant — only its *motion* matters.

We picked relative displacement over the old absolute-position model because the cursor-as-anchor scheme pinned the ship wherever the cursor sat on screen, which broke down at window edges and tied the feel to screen geography rather than to flying. We kept the smoothing pass (rather than a raw 1:1 mapping) at the player's request — the ship still chases a target, the target is just driven by motion now. `maxSpeed` survives only as a fixed teleport-guard clamp on the step; it is no longer an upgrade-scaled "chase speed."

**Pointer Lock is mandatory, not optional.** Relative control only works if movement is unbounded — a visible cursor stops producing deltas the instant it hits the window edge, freezing the ship mid-field. So gameplay runs under `requestPointerLock({ unadjustedMovement: true })` (raw, un-accelerated input where supported — Chromium yes, Safari/Firefox fall back silently to accelerated, which `sensitivity` absorbs). The system cursor is hidden by the lock; we add no reticle or custom cursor because the weapon fires straight up regardless of mouse position — the ship is the only thing the mouse controls and the only feedback needed.

The lock lifecycle follows one rule: **not in active gameplay ⇒ no lock; the click that returns you to gameplay re-locks.** The browser only grants Pointer Lock from inside a user gesture, so we cannot silently re-capture the mouse — every return-to-play transition rides an existing click (the menu **Play** button, the pause **Resume** button, an **upgrade-card pick**). Conversely every lock loss routes through `pointerlockchange` into the existing PauseOverlay: pressing **Esc** force-releases the lock (browser-enforced, un-preventable), and so do alt-tab and OS steals — all of them simply pause, which is why we *dropped* the manual Esc-keydown handler entirely. We must distinguish *expected* releases (we exit the lock ourselves when the Upgrade Prompt opens, so the cursor can pick a card) from *unexpected* ones, or the handler would stack a pause on top of an intentional release.

The **Engine** upgrade (id `moveSpeed`) is repurposed: it now scales **sensitivity** as its headline effect (how far the ship travels per unit of hand motion — the player's notion of "ship speed") and still bumps `followResponse` for snappier easing. `maxSpeed` is no longer touched by the upgrade.

One implementation consequence worth remembering: on respawn the ship resets to its start position, so the relative target point must reset too — otherwise the ship would immediately ease back toward a stale target left over from where it died.

Considered and rejected: **windowed pointer deltas** (no lock) — reintroduces the exact edge-freezing the change exists to kill; **raw 1:1 with no smoothing** — the player preferred keeping the eased chase; **a bespoke "Click to resume" gate** for lock loss — collapsed into the existing PauseOverlay once we realized Esc-releases-lock already maps cleanly onto Esc-pauses.
